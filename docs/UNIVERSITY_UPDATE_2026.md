# Обновление сайта по ТЗ от 6 ноября 2026

## Что реализовано

- API `POST /api/site/anonymous-message/`: обязательные subject/message (200/5000 символов), необязательные name/email (120/254), honeypot website, ограничение 5 запросов в час по хешированному техническому идентификатору. Авторизация не требуется. Сообщения не сохраняются в БД. Служебный From, пользовательский Reply-To. Ошибка SMTP возвращает 503; лог содержит только фиксированный код события.
- CMS: отдельный переключатель галереи, возможность скрывать секции, карточки и ссылки без удаления. Существующая явно включённая галерея и `/MaterialBaseGallery` сохраняются миграцией.
- `update_university_2026`: предпросмотр по умолчанию; применение только после создания защищённой резервной копии. Обновляет строковые поля, CKEditor HTML, вложенный JSON, SEO, медиа-подписи, footer и legacy PageContent. Последипломный раздел архивируется. Исторические новости и файлы не удаляются. Международный факультет медицины не переименовывается; название другого университета не изменяется.
- `/education`, `/education/student`, `/education/applicant`: редактируемые страницы RU/EN/KG, раздел «Программы» в Django Admin. Ссылки на действующие разделы вместо неподтверждённых тарифов/сроков. Существующие записи новых страниц не перезаписываются при повторном запуске.
- Публичные API исключают `/education/postgrad` и все его дочерние пути даже при случайной повторной публикации.
- Read-only аудит: `python manage.py audit_university_2026 [--strict]`.

## Настройка почты

В окружении, не в Git:

```dotenv
EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend
EMAIL_HOST=
EMAIL_PORT=587
EMAIL_HOST_USER=
EMAIL_HOST_PASSWORD=
EMAIL_USE_TLS=true
EMAIL_USE_SSL=false
DEFAULT_FROM_EMAIL=
ANONYMOUS_MESSAGE_RECIPIENT=
ANONYMOUS_MESSAGE_RATE=5/hour
REDIS_URL=
TRUSTED_PROXY_HOPS=0
```

Заполнить согласованный адрес получателя и подтверждённый служебный From. Для SSL/465 отключить TLS и включить SSL. Не использовать console email backend в публичном окружении: он печатает содержимое писем. REDIS_URL нужен для общего лимита между процессами/инстансами. TRUSTED_PROXY_HOPS задаётся по фактической доверенной цепочке reverse proxy; значение 0 не доверяет присланному клиентом X-Forwarded-For. Прокси должен заменять входящий X-Forwarded-For и ограничивать частоту/размер запросов на периметре. Кэш лимитера временно хранит хеши технических идентификаторов, без текста и контактных данных.

Мониторить события `anonymous_message_delivery_failed`, `anonymous_message_unconfigured`, HTTP 503/429 и отчёты о доставке у SMTP-провайдера. Успех API означает принятие письма SMTP-провайдером; получение в служебном ящике проверить отдельно. DRF throttle обеспечивает прикладное ограничение; строгий лимит при параллельных запросах обеспечивается также на reverse proxy.

## Порядок внедрения

Сначала staging, затем тот же проверенный порядок на production:

1. Сделать штатную резервную копию БД и проверить её восстановление. Зафиксировать текущие версии обоих приложений. Резервная копия должна храниться вне эфемерной файловой системы Heroku.
2. Установить зависимости, применить `python manage.py migrate --noinput`. Запустить штатную release-процедуру проекта. Исторические миграции вызывают команды импорта медиа до завершения всей схемы и могут вывести `skipped/partial`; после всех миграций выполнить штатный `python manage.py migrate_external_media --apply --strict` и проверить результат.
3. После всех seed/import-команд запустить `python manage.py update_university_2026` для предпросмотра.
4. Применить `python manage.py update_university_2026 --apply --backup /secure/persistent/cms-backup-2026.json`. Команда создаёт новый файл с правами 0600 и отказывается перезаписывать существующий. На Heroku безопасно выгрузить этот файл до завершения dyno либо использовать смонтированное защищённое хранилище. Это дополнительный снимок CMS, он не заменяет полную резервную копию БД.
5. Проверить/утвердить тексты новых страниц в Admin, официальное использование ИГН на трёх языках, получателя обращений и политику обработки данных. Подтвердить отдельные галереи переключателем в Admin. Переключатель имеет приоритет над устаревшим data.show_media_gallery.
6. Выполнить аудит, тесты и browser-проверку frontend; развернуть соответствующую версию frontend. Проверить реальные HTTP 301 на `/education/postgrad/*` и `/contacts` на используемом хостинге. В Vercel они заданы до SPA rewrites; при другом reverse proxy перенести эти правила в его конфигурацию. Удалить старые адреса из внешнего sitemap, если он ведётся отдельно: в репозиториях отдельного sitemap нет.
7. Отправить контрольное анонимное обращение без имени/email, проверить служебный ящик, Reply-To, rate limit, ошибку SMTP и мониторинг. Реальная почта в локальных тестах не отправляется.
8. Проверить реальные CMS-данные, мобильную версию, новости/документы, доступность, все языки, console/backend logs. Публиковать production только после staging-приёмки.

При последующих повторных seed/import-командах снова выполнять предпросмотр/применение обновления CMS: старые snapshot-файлы сохранены как исторические исходники и могут содержать старые наименования.

## Откат

Предпочтительно восстановить полную резервную копию БД и предыдущие релизы. Дополнительный CMS-снимок восстанавливается через `loaddata` в соответствующую схему. Он восстанавливает существовавшие строки; созданные после снимка новые страницы автоматически не удаляет — их следует снять с публикации, если требуется полный откат контента. Файлы оригинальных фотографий и документов обновление не удаляет.

## Автоматический production release (7 ноября 2026)

Procfile теперь выполняет только verify_media_storage → migrate → update_university_2026 --apply --database-backup. Повторный импорт старого WordPress/снимков, принудительная миграция внешних файлов и перезапись переводов удалены из автоматического релиза. Их можно запускать отдельно после проверки резервной копии при действительной необходимости.

Миграция 0012 создаёт ContentSnapshot: перед изменением CMS оригинальный сериализованный контент сохраняется в PostgreSQL в одной транзакции с обновлением. Снимок не публикуется в API/Admin и переживает перезапуск Heroku. Одинаковые снимки определяются по SHA-256; автоматического удаления снимков нет. Новости, партнёры и файлы в S3 не изменяются. Полная резервная копия Heroku Postgres дополнительно создаётся до внедрения. Новый снимок CMS не заменяет её.

Экспорт для восстановления: `python manage.py export_cms_snapshot ID --output /secure/cms-recovery.json`; затем восстановление соответствующей резервной копии через `loaddata` после проверки на тестовой БД. Это восстанавливает прежние строки, но не удаляет созданные после снимка страницы.

Почта: по указанию заказчика в .env.example и локальном игнорируемом .env задан пример admin@example.com. SMTP отсутствует; фактической доставки до настройки провайдера не будет. В Heroku используются Config Vars, а не локальный .env.
